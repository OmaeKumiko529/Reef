## 65.4 D. `preserveAspect` 使用点：不会压扁，但方形章会"按高适配"

**结论：`ApplySimple`（`UIArt.cs:82-89`，会置 `preserveAspect = true`）一共 3 个调用点，全部不会把贴图压扁；唯一实质问题是 `stamp_jimi`（128×128 方形）与写死的 `SealAspect = 176/72` 不匹配，会只占目标框 41% 宽度；`vignette` 反而不走 `ApplySimple`，保持 `preserveAspect = false`。**

| # | 调用点 | 矩形 vs 贴图 | 判定 |
|---|---|---|---|
| 1 | `Assets/Intelligence/CausalChainManager.cs:242` `ApplySimple(nodeImg, UIArt.BindingDot)` | 矩形由 `:236` `sizeDelta = new Vector2(UITheme.BindingDotSize, UITheme.BindingDotSize)` = **4×4 正方形**，贴图 8×8 正方形 → 长宽比一致（0.5× 缩小） | ✅ 不会被拉伸 |
| 2 | `Assets/UI/UIPanelChrome.cs:413`（`MakeSeal` 的 `Art` 子物体） | `:414` `sizeDelta = (size*2, size*2/SealAspect)`；`SealAspect`（`UIArt.cs:102`）= 176/72 → 唯一调用点 `size = StampSize*0.5 = 44`（`AgencyNavUI.cs:150-151`，`UITheme.StampSize = 88`）→ 矩形 **88×36**，贴图 176×72 → 正好 0.5× | ✅ 已渗透/未开放两枚横章完美贴合 |
| 3 | `Assets/UI/UIPanelChrome.cs:448`（`SetStamp`） | `:451` `sizeDelta = (StampSize*2, StampSize*2/SealAspect)` = **176×72**，贴图 176×72 → 1:1 | ✅（但 `SetStamp` 无调用点，见 65.6） |

`stamp_jimi`（128×128）走上面第 2/3 条：`preserveAspect = true` 保证**不会被压扁**（fit = min(176/128, 72/128) = 0.5625 → 实际渲染 72×72，居中，左右留白），但：
- 它比其他两枚横章"窄" 176→72（41%），且宽高比与 `SealAspect` 常量无关，`sizeDelta` 那两行对它是**无效计算**；
- 也就是说"机密"章一旦接线，视觉上会比"未开放/已渗透"小一截（高度相同 72，宽度差 2.4×）。修法：把 `sizeDelta` 从常量改成按 `sprite.rect.width / sprite.rect.height` 推导（`UIArt.cs` 里加一个 `AspectOf(Sprite)`），或在 `MakeSeal`/`SetStamp` 里对 1:1 章单独给 `size*2 × size*2`。

反向一条：`vignette`（`UIArt.cs:124-138`）**没有**走 `ApplySimple`，而是手写 `img.sprite/type/color/raycastTarget`，因此 `preserveAspect` 保持 Unity 默认 `false` → 256×256 被拉伸到 1920×1080（+40 外扩），径向暗角会变成"左右先暗、上下后暗"的椭圆暗角（若想要正圆暗角需 `preserveAspect = true`，但那样左右会留白，所以当前写法也许是刻意的——见 65.9 ❓）。

## 65.5 E. 叠层点击：不会吃掉点击（逐条证据）

**答"能不能抓"：你列的四种改坏全部会被抓住** —— 少一个 PNG（M1：H1a+H1b 双 FAIL）、border 改错（M3：H2 FAIL）、wrap 改回 1（M2：H2 FAIL）、删掉一处 `raycastTarget = false`（M6：H3 FAIL）。另外 sortingOrder 被改小或整行删掉也会 FAIL（M8/M11），meta 被删会 FAIL（M12），名字打错会 FAIL（M9）。**剩下的 4 个假绿里，3 个建议修（都是护栏强度，不是当前产物缺陷）：**

- 🟠 **V2-1 `textureCompression` / `sRGBTexture` / `maxTextureSize` 没被任何断言钉住。** H2 的 needle 数组只有 5 项（`Tools/uipolish-check.ps1:409`：`textureType: 8` / `spriteMode: 1` / `enableMipMap: 0` / `spriteMeshType: 0` / `alphaIsTransparency: 1`），M5 证明把 `textureCompression` 改成 1（BC/DXT）依然全绿——而 14 张纸上纹理会因此出现块状压缩伪影，且生成端自检（`gen-uiart.py:622-632`）也不查这一项。修法：`:409` 数组补 `'textureCompression: 0'`、`'sRGBTexture: 1'`、`'maxTextureSize: 256'`（三个字符串同时补进 `gen-uiart.py:622` 的 checks 更稳）。
- 🟠 **V2-2 border 只校验"meta == 生成器"，没有钉住正确值。** `:412-418` 用生成器的 `add("name", (l,b,r,t))` 元组去比对 meta，所以 M4（两边一起改成 2）全绿——而 border 与用途是硬绑定（paper 18 / btn 12 / rule_ring* 8 / titleplate·dossier·redaction 只切左右 / 其余 0），改错会让 9-slice 边框挤压或整圈错位。修法：在脚本里放一张 14 条的期望 border 表（或哈希），断言"meta 的 border == 期望表"而不是"== 生成器"。同理 `paper_plate_9s` 的 `paper 18` 一旦在生成器里被改成别的值，H2 也发现不了。
- 🟠 **V2-3 H3 对"新增叠层图形"和"第二个叠层画布"是盲的。** `:433` 只数 `raycastTarget = false` 的出现次数并要求 ≥2；实测基线正好是 **2 处**（`UIArt.cs:137` 暗角、`:155` AddTiled 的 RawImage），所以删任意一处都会 FAIL（M6 ✅），但**新增**一个 `raycastTarget = true` 的图形不会（M7 假绿）；`:436` 也只查 `blocksRaycasts = false` 是否存在，不查"每个叠层画布都挂了 CanvasGroup"。当前不构成 bug——`UIArt.cs:118-120` 的 `CanvasGroup.blocksRaycasts = false` 已经让整层不吃点击（双保险），但这层保险一旦被谁顺手删掉、或有人再建第二块没挂 CanvasGroup 的叠层，H3 抓不到。修法二选一：①断言 `Count-Pat 'CreateCanvas'` 与 `Count-Pat 'blocksRaycasts = false'` 相等；②代码侧在 `BuildScreenOverlays` 末尾统一 `foreach (var g in canvas.GetComponentsInChildren<Graphic>(true)) g.raycastTarget = false;`，门禁只断言这个循环存在（更省事，也一劳永逸）。
- 🟡 **V2-4（可不修）H1b 的取名字正则不认大写名。** `:398` 的 `(?:Get|TextureOf)\("([a-z0-9_]+)"\)` 只匹配小写+数字+下划线；实测 `[regex]::Matches('Get("HalftoneTile") Get("ok_name") TextureOf("vignette")', ...)` 只命中 `ok_name,vignette`。所以 M10（`Get("Vignette")`）会让该名字从被检查集合里消失，而 `:401` 的 `$refNames.Count -ge 10` 在 13 个引用时仍然成立 → 静默回退纯色的经典场景恰好逃过门禁。当前 14 个名字全小写 ✅ 无实害；把字符类放宽成 `[A-Za-z0-9_]+` 即可。
- 🟡 V2-5（可不修）次要口径：needle 用子串匹配（`:409-410`），`textureType: 80` 这类非法值理论上也会 PASS；`$diskNames` 为空时 H2 的循环体不执行会"空过"（`:405`），但 H1a/H1b 会同时 FAIL，聚合口径仍安全。路径方面没有风险：`$root = Split-Path -Parent $PSScriptRoot`（`:9`）与 CWD 无关，实测从 `C:\` 运行仍 45/0；且 H 块只用 `[regex]` + `[System.IO.File]::ReadAllText` + `Test-Path -LiteralPath`，**没有用 `ConvertFrom-Json`**，PS 5.1 无兼容问题。
